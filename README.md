## 它解决什么问题

手上有几台 VPS，每台有月流量配额。跑超了轻则扣费，重则被商家停机。麻烦的是：

- **计费口径各家不同**。有的按进出流量相加，有的只按进出中较大的那个方向算（俗称"单向流量"）。
- **账单日各家不同**。有的 1 号，有的 8 号，还得按机房所在时区算。
- **跑满之后要有人管**。半夜跑满没人处理，第二天就是超额账单或者停机。
- **主力机器一挂，指向它的域名得赶紧切走**。

如果这几台机器还互相做中转，又多一层麻烦：转发规则散落在各台机器的 `nftables` 里，
改一次要挨个登录；哪条规则吃掉了多少流量，也没地方看。

这个面板把上面这些做成自动的，并把转发规则收拢到一处统一管理。

## 主要功能

### 流量统计与配额

- 四种计费口径：双向相加 / 单向取大 / 仅出站 / 仅入站
- 计费倍率，用于校准网卡统计与商家账单之间的几个百分点差异
- 每台机器独立设置清零日（1–31 号）与时区，31 号遇小月自动落到月末
- 小时级流量曲线，历史账单周期自动归档

### 流量耗尽后的处置

每台机器单独配置，默认不做任何操作：

| 方式 | 说明 |
|---|---|
| SSH 远程关机 | 面板直连机器 SSH。**探针进程死了也照样能关**，最可靠 |
| 探针本地关机 | 由探针执行关机，依赖探针存活 |
| 执行自定义命令 | 例如 `systemctl stop xray`，停服务但保留 SSH |
| 仅切换解析 + 告警 | 不动机器 |

### 域名故障切换

- 支持 Cloudflare、腾讯云 DNSPod、阿里云 DNS
- 按优先级选主，触发条件可分别开关：流量耗尽 / 机器离线 / 到达预警线
- **防误切**：探针失联后再做一次 TCP 拨测确认，连续失败 N 次才判定下线，两次切换之间有冷却期
- **切换演练**：只计算不改动，告诉你此刻会切到哪台、每个候选为什么被淘汰

### 端口转发

- 两种转发模式，可逐跳混用：

  | 模式 | 实现 | 特点 |
  |---|---|---|
  | 内核态（默认） | nftables DNAT | 零拷贝，开销最低，TCP / UDP / TCP+UDP 全支持 |
  | 用户态 | 探针内嵌 TCP relay | 每跳单独建连接，避免多跳串联时 TCP 拥塞叠加；带预连接池省一次握手往返。仅支持 TCP |

- **多跳链路**：入口 → 中转 → … → 目标。监听端口留空即从该机器配置的端口范围内随机分配
- **一键链路测试**：逐跳让每台机器去拨自己的下一跳，直接指出断在第几段，
  并带回该机器的转发能力自检（nftables、内核转发开关、监听状态、已生效规则数）
- 目标支持域名，探针定期重解析，解析结果变化后自动跟进
- 每跳可单独限速（tc HTB）
- 自动兼容 Docker / ufw：往它们预留的用户扩展链插入放行规则，
  避免包 DNAT 成功却被其他工具的 FORWARD 策略丢弃
- **转发流量不重复计费**，详见[设计说明](#二转发流量不重复计费)

### 其他

- Telegram / Webhook 通知
- 事件日志：上下线、流量预警、耗尽、关机动作、域名切换、周期清零、转发下发
- SSH 凭据与 DNS API 凭据使用 AES-256-GCM 加密存储
- SSH 主机密钥 TOFU 校验，机器被替换会拒绝连接并告警

## 架构

```
┌──────────────────┐   WebSocket：上报计数器 / 下发指令与转发规则   ┌──────────────┐
│                  │◄────────────────────────────────────────────►│   节点探针     │
│      面板         │                                              │  vps-agent   │
│   vps-panel      │   SSH 远程关机（探针进程死了也能用）             │              │
│                  │─────────────────────────────────────────────►│   你的 VPS    │
│  SQLite 流量账本   │                                              └──────────────┘
│  + 内嵌前端       │   修改解析记录
│                  │──────────────────► Cloudflare / DNSPod / 阿里云 DNS
└──────────────────┘
```

**职责划分**：探针只负责上报原始计数器和执行指令，不记账、不判断配额、不做任何决策；
所有账本与决策都在面板端。这样机器怎么重启，账本都不会错乱。

## 快速开始

### 面板端（一台机器装一次）

```bash
curl -fsSL https://raw.githubusercontent.com/zxcll/vps-panel/main/install.sh -o install.sh
sudo bash install.sh panel install
```

首次启动会打印一次随机管理员密码，请及时保存。没看到的话：

```bash
journalctl -u vps-panel | grep -A6 初始化
```

不带参数运行 `sudo bash install.sh` 会进入交互菜单，安装、启动、停止、重启、
查看日志、修改配置、卸载都在里面。

国内机器连不上 GitHub 时，加个加速前缀：

```bash
GITHUB_PROXY=https://ghfast.top/ sudo bash install.sh panel install
```

### 节点端（每台被监控的机器）

在面板里新建节点，页面会给出一条带密钥的安装命令，复制到那台机器上执行即可。

也可以手动安装：

```bash
sudo bash install.sh agent install --server wss://panel.example.com --secret 节点密钥
```

> 端口转发需要探针以 root 运行，并依赖 `nftables` 与 `iproute2`。安装脚本会自动安装；
> 装不上只会警告，流量监控功能不受影响。不需要转发功能的话，把探针的
> `VPS_AGENT_ALLOW_FORWARD` 设为 `false`。

### Docker

```bash
cp config.example.yaml config.yaml   # 按需修改
docker compose up -d
```

### 从源码编译

只需要 Go 1.26，**不需要 Node** —— 前端是浏览器直接可运行的 ES 模块，由 `go:embed` 打进二进制。

```bash

```

## 设计说明

这个项目有两条决定性的设计，都围绕同一个目标：**流量账本不能算错。**
账本错了不只是数字难看——超额动作里有真关机，算错就是机器被误关。

### 一、账本存在面板端

**机器重启后 `/proc/net/dev` 的计数器会归零。** 如果让机器自己记账，重启就丢数据。

所以分工是：

- 探针**只上报网卡累计计数器的原始值**，不做任何记账与判断
- 面板**负责做差值累加**，靠 `boot_id`（`/proc/sys/kernel/random/boot_id`，每次开机必变）识别重启

机器重启时 `boot_id` 变了，面板即可判定计数器已归零，把当前值整个计入本周期。
最坏情况只丢失"最后一次上报到断电"之间的流量（默认上报间隔 30 秒）；
探针收到 `SIGTERM` 时还会补报一次，正常重启连这一点都不丢。

由此得到三条保证，均有自动化测试守护：

| 场景 | 结果 |
|---|---|
| 重复上报同一份报文 | 做差得 0，天然幂等 |
| 探针重启 / 崩溃 / 被杀 | 账本不受影响 |
| 面板重启 | 基线在数据库里，继续累加 |

### 二、转发流量不重复计费

先澄清一个容易误解的点：**转发流量本来就已经计入配额了，而且计得没错。**

一份流量经过中转机时要进来一次、再出去一次，网卡上因此记两遍——
商家的计量口径也是这么算的：

| 观察点 | 入站 | 出站 |
|---|---|---|
| 中转机网卡 `/proc/net/dev` | 上行 + 下行 | 上行 + 下行 |
| 商家上游交换机 | 上行 + 下行 | 上行 + 下行 |
| nftables 每条规则的计数 | 上行 | 下行 |

所以真正的风险只有一个：把 nftables 的规则计数**再加进**节点账本。于是定下一条铁律：

> nftables 计数走独立的 `forward_*` 表，只用于分账展示，
> **一个字节都不进 `node_usage`**，也不参与配额判定、超额动作和 DNS 切换。

代价是界面上会出现两个口径的数字，用户会问「规则加起来才 50G，机器怎么用了 100G」。
所以面板替你换算好了「**实际消耗流量**」这一列：

| 计费口径 | 一条规则（上行 U、下行 D）实际消耗 |
|---|---|
| 双向相加 | `2 × (U + D)` |
| 单向取大 / 仅出站 / 仅入站 | `U + D` |

节点详情页据此把本周期用量拆成「转发消耗的」与「机器自己用掉的」两部分。

**转发计数的重启安全性**沿用同一套做法：探针只报单调递增的累计值，面板做差值。
`nft` 每次 apply 都会把计数清零，因此探针在删表**之前**先采样结转，改规则不会丢掉那一段流量；
只有探针的状态文件真的丢失才会更换 `epoch`，面板见到 `epoch` 变化即按"计数器归零"处理——
它在这里扮演的正是 `boot_id` 的角色。

## 部署建议

面板保存着各节点的 SSH 凭据，是高价值目标。**不建议直接暴露在公网。**

推荐只监听 `127.0.0.1`，前面用 Nginx 反代 + HTTPS：

```nginx
server {
    listen 443 ssl http2;
    server_name panel.example.com;

    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;

        # 探针走 WebSocket 长连接，这两行必须有
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 长连接不能被反代掐断
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

反代后面记得开启 `trust_proxy_headers: true`（或环境变量 `PANEL_TRUST_PROXY=true`），
否则日志里记录的是反代的 IP。

**需要备份的文件**（都在数据目录下）：

- `panel.db` —— 流量账本与全部配置
- `master.key` —— 凭据解密密钥。**丢失后所有 SSH 密码和 DNS 凭据都无法解开，只能重新填写**

## 配置

启动期配置见 [`config.example.yaml`](config.example.yaml)。
运行期参数（离线判定阈值、失败次数、切换冷却、通知渠道、数据保留天数）
在面板的「设置」页面里修改，无需重启。

几个值得说明的参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| 离线判定阈值 | 90 秒 | 心跳超过这个时长没来即认为探针失联。探针默认 30 秒上报一次，留了三倍余量 |
| 连续失败次数 | 3 | 达到这个次数才真正判定下线，避免一次网络抖动就把域名切走 |
| TCP 拨测 | 开启 | 探针失联后再拨一次端口确认。探针进程崩了但机器仍在跑业务时不应切换 |
| 切换冷却 | 300 秒 | 两次自动切换的最小间隔，防止状态在临界点抖动导致解析来回改。手动切换不受此限制 |
| 计费倍率 | 1.0 | 网卡层统计与商家计量口径通常差几个百分点，用它校准 |

> 配额建议设为商家标称值的 95% 左右，留一点余量。

## 测试与验证

```bash
make test       # 单元测试
make test-race  # 带竞态检测
make e2e        # 端到端：起真实面板 + 探针，31 项断言
```

端到端脚本覆盖的场景：

**流量账本**

1. 探针上报 → 面板账本累加
2. **机器重启（`boot_id` 变化）→ 账本继续累加而不是归零**
3. 面板进程重启 → 账本不丢
4. 重复上报同一份报文 → 不重复计账
5. 单向计费口径确实按较大方向计算

**配额与处置**

6. 流量到达预警线 → 产生预警事件
7. 流量耗尽 → 状态转超额、写入事件、不误触发关机
8. 探针后续心跳不会把超额状态刷回在线
9. 手动清零 → 用量归零、上周期归档、超额限制解除

**端口转发**

10. 多跳规则的入口地址与逐跳目标推导正确
11. **转发计数只进转发账本，节点账本一个字节都不多**
12. 实际消耗流量的换算结果与节点用量对得上
13. 转发计数重复上报不重复计账、`epoch` 变化按归零处理
14. 上报里带已删除的跳时不会让整次上报失败
15. 监听端口留空时确实从配置的端口范围内分配
16. 链路测试逐跳返回结果，并带回节点侧的转发能力自检
17. 节点被禁用时规则明确报告未生效原因

另外：DNS 三家服务商的签名与请求构造有对应的单元测试（`httptest` mock）；
选主逻辑（优先级、超额淘汰、冷却期、全员不健康时保持现状）有独立测试。

转发数据面的单元测试**全部不需要 root**：nftables 规则渲染与计数解析是纯字符串/JSON 处理，
内核后端在测试中替换为假实现，用户态 relay 与预连接池则起真实的本地监听来测
（包含「连接池探活不能吃掉上游先发来的首字节」这条）。
真正需要 root 的只有把规则落到内核这一步。

> 首次配置真实域名时，建议先用面板上的「切换演练」确认选主结论符合预期，再交给自动切换。

## 项目结构

```
cmd/panel、cmd/agent        两个程序入口
internal/
  ingest/                   计数器 → 增量 → 账本（重启安全的核心）
  quota/                    计费口径与配额判定
  billing/                  账单周期边界（重置日 + 时区）
  failover/                 健康判定、选主、DNS 切换
  dns/                      Cloudflare / DNSPod / 阿里云，手写签名不引 SDK
  forward/                  转发数据面：nftables 渲染/应用/计数、用户态 relay、预连接池
  forwardplan/              多跳展开与端口分配（纯函数）
  tc/                       HTB 限速
  resolver/                 转发目标的域名解析
  action/                   SSH 远程关机、探针指令下发
  engine/                   后台调度：周期滚动、配额判定、动作编排
  server/                   HTTP 接口、WebSocket 探针接入、内嵌前端
  agent/                    探针：采集、上报、执行指令、落地转发规则
web/                        前端源码（Vue 3 ESM，无构建步骤）
```

## 已知限制

**流量统计**

- 流量口径与商家不完全一致。`/proc/net/dev` 统计的是网卡层字节，商家可能按 IP 层计算，
  是否含协议开销也各家不同，通常差几个百分点。用计费倍率校准。
- 容器里跑探针时，`/proc/sys/kernel/random/boot_id` 取到的是宿主机的，多个容器会撞成同一个值。
  用 `VPS_AGENT_BOOT_ID` 给每个容器指定不同的值。

**处置动作**

- 面板只能关机，不能开机。没有带外管理权限，被关掉的机器需要到服务商后台手动开启。
  新周期开始时面板会解除超额限制，但机器仍需自行启动。

**端口转发**

- 限速只作用于出方向，这是 tc 的固有限制。对中转机影响不大：
  转发的两个方向都是本机出方向，因此一条规则的上下行会共享同一份带宽。
- 需要探针以 root 运行，且机器上有 `nftables` 与 `iproute2`。
- **云服务商的安全组 / 防火墙管不了**。转发用的入口端口仍需自行到服务商控制台放行，
  那一层在机器外面。链路测试中「面板 → 入口」不通、但每一跳都通，基本就是这个原因。
- 修改转发规则会重置该规则的流量统计。跳是整组重写的，跳的 ID 变化，分账随之从头开始——
  改了跳序之后，旧的用量本来也对不上新拓扑。只切换「启用 / 停用」不会重置。

**其他**

- 单管理员账号，没有多用户与角色权限。
