## 它解决什么问题

手上有几台 VPS，每台有月流量配额。跑超了轻则扣费，重则被商家停机。麻烦的是：

- **计费口径各家不同**。有的按进出流量相加，有的只按进出中较大的那个方向算（俗称"单向流量"）。
- **账单日各家不同**。有的 1 号，有的 8 号，还得按机房所在时区算。
- **跑满之后要有人管**。半夜跑满没人处理，第二天就是超额账单或者停机。
- **主力机器一挂，指向它的域名得赶紧切走**。

如果这几台机器还互相做中转，又多一层麻烦：转发规则散落在各台机器的 `nftables` 里，
改一次要挨个登录；哪条规则吃掉了多少流量，也没地方看。

这个面板把上面这些做成自动的，并把转发规则收拢到一处统一管理。

## 主要功能

### 流量统计与配额

- 四种计费口径：双向相加 / 单向取大 / 仅出站 / 仅入站
- 计费倍率，用于校准网卡统计与商家账单之间的几个百分点差异
- 每台机器独立设置清零日（1–31 号）与时区，31 号遇小月自动落到月末
- 小时级流量曲线，历史账单周期自动归档

### 流量耗尽后的处置

每台机器单独配置，默认不做任何操作：

| 方式 | 说明 |
|---|---|
| SSH 远程关机 | 面板直连机器 SSH。**探针进程死了也照样能关**，最可靠 |
| 探针本地关机 | 由探针执行关机，依赖探针存活 |
| 执行自定义命令 | 例如 `systemctl stop xray`，停服务但保留 SSH |
| 仅切换解析 + 告警 | 不动机器 |

### 域名故障切换

- 支持 Cloudflare、腾讯云 DNSPod、阿里云 DNS
- 按优先级选主，触发条件可分别开关：流量耗尽 / 机器离线 / 到达预警线
- **防误切**：探针失联后再做一次 TCP 拨测确认，连续失败 N 次才判定下线，两次切换之间有冷却期
- **切换演练**：只计算不改动，告诉你此刻会切到哪台、每个候选为什么被淘汰

### 端口转发

- 两种转发模式，可逐跳混用：

  | 模式 | 实现 | 特点 |
  |---|---|---|
  | 内核态（默认） | nftables DNAT | 零拷贝，开销最低，TCP / UDP / TCP+UDP 全支持 |
  | 用户态 | 探针内嵌 TCP relay | 每跳单独建连接，避免多跳串联时 TCP 拥塞叠加；带预连接池省一次握手往返。仅支持 TCP |

- **多跳链路**：入口 → 中转 → … → 目标。监听端口留空即从该机器配置的端口范围内随机分配
- **多入口**：入口那一跳可以配好几台机器，它们**共用同一个监听端口**。
  把这几台一起加进[域名故障切换](#域名故障切换)的候选列表，域名切到哪一台转发都还通，
  客户端连的地址端口一个字都不用改。中间的中转跳只能是一台——链路中段一旦分叉，
  「上一跳该往哪发」就没有定义了
- **一键链路测试**：逐段让每台机器去拨自己的下一跳（最后一跳才拨落地目标），
  直接指出断在哪一段，并带回该机器的转发能力自检
  （nftables、内核转发开关、监听状态、已生效规则数）。
  每一段还会**单独量一次真实网络延迟**，详见[设计说明](#四链路测试为什么要量两个耗时)
- 目标支持域名，探针定期重解析，解析结果变化后自动跟进
- 每跳可单独限速（tc HTB）
- 自动兼容 Docker / ufw：往它们预留的用户扩展链插入放行规则，
  避免包 DNAT 成功却被其他工具的 FORWARD 策略丢弃
- **转发流量不重复计费**，详见[设计说明](#二转发流量不重复计费)

### 阿里云 CDT 管理

对着 [AliCDT-Manager](https://github.com/lillinlin/AliCDT-Manager) 的功能重写了一份，
和上面的节点账本**完全分开**——阿里云的计量口径和探针的网卡口径不是一回事，见[设计说明](#三阿里云-cdt-独立记账)。

- 多账号聚合，AccessKey 用 AES-256-GCM 加密存储；**账号站点自动识别**——
  拿两个站点的账单接口各试一次，不用自己记账号是在哪注册的（地域推不出站点：
  国际站账号照样能在杭州开机器）
- **免费额度分两个池算**：中国内地 20 GB/月、非中国内地 200 GB/月，**只统计出方向**。
  两个池分别判，任意一个越线就熔断——加起来对总额度判的话，中国内地那 20 GB 跑满了也看不出来
- 流量或待还金额超阈值 → 自动停机（可选节省模式，停机不计费）
- 抢占式实例保活：被回收后自动拉起，可用区售罄只告警一次，恢复后再报
- 定时开关机、账期翻页自动恢复、每日用量汇报
- 逐地域明细，直接看得到哪个地域归在哪个池、吃掉了多少额度
- **「每天还能用多少」**：`(熔断线 − 已用) ÷ 本月剩余天数`。比一个百分比进度条
  有用——直接告诉你按这个节奏够不够撑到月底
- **同步间隔每个账号自己配**（秒，默认 300）。流量、账单、实例状态、保活都按它走；
  定时开关机不受影响，固定一分钟看一次（按钟点触发的东西，间隔拉长会错过时间点）。
  实例正在开机/关机时自动加快到 15 秒一次，省得点完开关机干等一整个周期

> **CDT 用量不是实时的。** 阿里云那边的统计本身就有小时级延迟，面板查得再勤也是
> 同一个值——把同步间隔调小主要是让**保活更快**（实例被回收后最多隔这么久被拉起来）。
> 想更早知道流量涨了，看这些机器在「节点管理」里的实时用量，那是探针每 30 秒直接
> 从网卡读的。

> 只有勾了「受守护」的实例才会被停机 / 拉起 / 定时管到，其余的面板只看不动。
> 需要的 RAM 权限：CDT（读流量）、ECS（读实例，用到开关机才要写权限）、BSS（读账单，可选）。
> **只做监控的话建议只给只读策略。**

### 面板自更新

设置页显示当前版本和 GitHub 上的最新版，有新版就能**直接在页面上点一下升级**，
不用 SSH。和探针升级共用同一套安全机制（见下），另外多一道 **SHA256 校验**——
探针的二进制是从面板下的，面板的是从公网下的，可信度不一样。

国内机器连不上 GitHub 时，在设置里填一个加速前缀即可（和 `install.sh` 的
`GITHUB_PROXY` 一个意思）。升级会顺带把 `data/agents/` 下各架构的探针也更新到同版本。

> 数据库、配置、`master.key` 都不受影响。校验不过就不动旧版本，
> 旧版还留一份 `.old` 可以随时换回去。

### 探针远程升级

节点多了之后，每次发版挨台 SSH 上去跑安装脚本太蠢。面板本来就存着各架构的探针二进制、
也本来就有一条到每台机器的长连接，把这两件事接起来即可：

- 节点列表上直接显示每台机器的探针版本，落后的标出来
- 单台升级，或一键把所有在线节点都升一遍（串行做，不会把面板的上行打满）
- 升级前后各上报一次流量，**升级过程不丢账**

安全上最要紧的是「别把程序砸了」——机器可能远在天边，SSH 未必配过。所以拿到新二进制后
会先**校验它真的能跑**（ELF 文件头 + 实际执行一次 `--version`），过了才替换，
旧版本留一份 `.old` 可以随时 `mv` 回来。任何一步失败都不动旧二进制。
不想要这个功能就给探针加 `--allow-upgrade=false`。

**不会越升越占地方**：`.old` 每次覆盖，始终只有一份；下载到一半被杀留下的临时文件
在下次启动和下次升级时都会清掉。所以无论升多少次，磁盘上只比原来多一个二进制。

> 这套逻辑在 `internal/selfupdate` 里，面板和探针**共用同一份**——
> 换错了就是把程序自己砸了，两份实现迟早会分叉，而分叉出去的那份一定是没人测的那份。

### 节点关联阿里云 CDT

把节点和 CDT 实例关联起来（**按公网 IP 自动建议**，不用在一串 `i-xxxx` 里手动认），
面板就知道这台机器背后是哪个阿里云实例。带来两件事：

**一、计划内停机不再被当成事故。** CDT 按计划停机（定时关机、流量熔断）时，
关联的节点会被标成「计划内停机」而不是「离线」：

| | 普通掉线 | 计划内停机 |
|---|---|---|
| 掉线告警 | 发 | **不发**（那是面板自己停的） |
| 域名切换 | 切走 | **默认不切**，每条记录可单独打开 |
| 恢复时的通知 | 「节点已恢复」 | 「节点已开机」 |

> 默认不切域名是有代价的：停机期间域名会一直指着一台关着的机器。
> 希望流量走别处，就在域名记录上打开「计划内停机时也切走」。

**二、多一种超额动作：CDT 节省关机。** 节点流量跑满时通过阿里云 API 停机，
比 SSH / 探针关机强在两点——**停机后不再收实例费**，而且探针死了、SSH 连不上也照样能关。

### 其他

- Telegram / Webhook 通知
- **节点上线通知**：探针首次接入、掉线后恢复、从计划内停机中开机都会通知，
  三种情形文案不同。掉线通知一直会发；上线通知有人嫌吵，设置里可以关
- 事件日志：上下线、流量预警、耗尽、关机动作、域名切换、周期清零、转发下发
- SSH 凭据与 DNS API 凭据使用 AES-256-GCM 加密存储
- SSH 主机密钥 TOFU 校验，机器被替换会拒绝连接并告警

## 架构

```
┌──────────────────┐   WebSocket：上报计数器 / 下发指令与转发规则   ┌──────────────┐
│                  │◄────────────────────────────────────────────►│   节点探针     │
│      面板         │                                              │  vps-agent   │
│   vps-panel      │   SSH 远程关机（探针进程死了也能用）             │              │
│                  │─────────────────────────────────────────────►│   你的 VPS    │
│  SQLite 流量账本   │                                              └──────────────┘
│  + 内嵌前端       │   修改解析记录
│                  │──────────────────► Cloudflare / DNSPod / 阿里云 DNS
└──────────────────┘
```

**职责划分**：探针只负责上报原始计数器和执行指令，不记账、不判断配额、不做任何决策；
所有账本与决策都在面板端。这样机器怎么重启，账本都不会错乱。

## 快速开始

### 面板端（一台机器装一次）

```bash
curl -fsSL https://raw.githubusercontent.com/zxcll/vps-panel/main/install.sh -o install.sh
sudo bash install.sh panel install
```

首次启动会打印一次随机管理员密码，请及时保存。没看到的话：

```bash
journalctl -u vps-panel | grep -A6 初始化
```

不带参数运行 `sudo bash install.sh` 会进入交互菜单，安装、启动、停止、重启、
查看日志、修改配置、卸载都在里面。

国内机器连不上 GitHub 时，加个加速前缀：

```bash
GITHUB_PROXY=https://ghfast.top/ sudo bash install.sh panel install
```

### 升级到最新版

```bash
sudo bash install.sh panel upgrade
```

配置、数据库、主密钥都不动，只换二进制并顺带把各架构的探针更新到最新。
**节点上的探针不用再挨台 SSH 升级**——面板升完之后到「节点管理」页点「升级探针」即可，
详见[探针远程升级](#探针远程升级)。

### 节点端（每台被监控的机器）

在面板里新建节点，页面会给出一条带密钥的安装命令，复制到那台机器上执行即可。

也可以手动安装：

```bash
sudo bash install.sh agent install --server wss://panel.example.com --secret 节点密钥
```

> 端口转发需要探针以 root 运行，并依赖 `nftables` 与 `iproute2`。安装脚本会自动安装；
> 装不上只会警告，流量监控功能不受影响。不需要转发功能的话，把探针的
> `VPS_AGENT_ALLOW_FORWARD` 设为 `false`。

### Docker

```bash
cp config.example.yaml config.yaml   # 按需修改
docker compose up -d
```

## 设计说明

这个项目有几条决定性的设计，前三条都围绕同一个目标：**账本不能算错。**
账本错了不只是数字难看——超额动作里有真关机，算错就是机器被误关。
第四条讲的是另一类「数字骗人」：量出来的东西根本不是你以为的那个东西。

### 一、账本存在面板端

**机器重启后 `/proc/net/dev` 的计数器会归零。** 如果让机器自己记账，重启就丢数据。

所以分工是：

- 探针**只上报网卡累计计数器的原始值**，不做任何记账与判断
- 面板**负责做差值累加**，靠 `boot_id`（`/proc/sys/kernel/random/boot_id`，每次开机必变）识别重启

机器重启时 `boot_id` 变了，面板即可判定计数器已归零，把当前值整个计入本周期。
最坏情况只丢失"最后一次上报到断电"之间的流量（默认上报间隔 30 秒）；
探针收到 `SIGTERM` 时还会补报一次，正常重启连这一点都不丢。

由此得到三条保证，均有自动化测试守护：

| 场景 | 结果 |
|---|---|
| 重复上报同一份报文 | 做差得 0，天然幂等 |
| 探针重启 / 崩溃 / 被杀 | 账本不受影响 |
| 面板重启 | 基线在数据库里，继续累加 |

### 二、转发流量不重复计费

先澄清一个容易误解的点：**转发流量本来就已经计入配额了，而且计得没错。**

一份流量经过中转机时要进来一次、再出去一次，网卡上因此记两遍——
商家的计量口径也是这么算的：

| 观察点 | 入站 | 出站 |
|---|---|---|
| 中转机网卡 `/proc/net/dev` | 上行 + 下行 | 上行 + 下行 |
| 商家上游交换机 | 上行 + 下行 | 上行 + 下行 |
| nftables 每条规则的计数 | 上行 | 下行 |

所以真正的风险只有一个：把 nftables 的规则计数**再加进**节点账本。于是定下一条铁律：

> nftables 计数走独立的 `forward_*` 表，只用于分账展示，
> **一个字节都不进 `node_usage`**，也不参与配额判定、超额动作和 DNS 切换。

代价是界面上会出现两个口径的数字，用户会问「规则加起来才 50G，机器怎么用了 100G」。
所以面板替你换算好了「**实际消耗流量**」这一列：

| 计费口径 | 一条规则（上行 U、下行 D）实际消耗 |
|---|---|
| 双向相加 | `2 × (U + D)` |
| 单向取大 / 仅出站 / 仅入站 | `U + D` |

节点详情页据此把本周期用量拆成「转发消耗的」与「机器自己用掉的」两部分。

**转发计数的重启安全性**沿用同一套做法：探针只报单调递增的累计值，面板做差值。
`nft` 每次 apply 都会把计数清零，因此探针在删表**之前**先采样结转，改规则不会丢掉那一段流量；
只有探针的状态文件真的丢失才会更换 `epoch`，面板见到 `epoch` 变化即按"计数器归零"处理——
它在这里扮演的正是 `boot_id` 的角色。

### 三、阿里云 CDT 独立记账

同一条铁律的第三次应用：**口径不同的两份数字，绝不能混进同一个账本。**

阿里云 CDT 的计量和探针的网卡计量根本不是一回事：

| | 探针（node_usage） | 阿里云 CDT |
|---|---|---|
| 统计单位 | 单台机器 | 整个账号 |
| 方向 | 进出都算（看计费口径） | **只算出方向** |
| 额度 | 每台机器一个配额 | **分中国内地 / 非中国内地两个池** |
| 周期边界 | 每台机器自己的清零日 + 时区 | 每自然月 1 日 0 点（北京时间） |

所以 CDT 用独立的 `cdt_*` 表，不进 `node_usage`、不参与节点配额判定和 DNS 切换。
界面上也不放在一起比——那只会让人以为两个数字应该对得上。

顺带修了参考实现的一个口径错误：把两个池加起来对着 220 GB 判，
会在中国内地那 20 GB 早就跑满时仍然显示「才用了 18%」。
香港、澳门、台湾的地域 ID 虽然是 `cn-` 开头，计费上却属于**非中国内地**——
漏掉这条例外，一台正常跑的香港机器会被算进只有 20 GB 的池子，很快就被误判成超额停机。
这段判定是纯函数，有专门的单元测试钉着。

### 四、链路测试为什么要量两个耗时

链路测试让每台机器去拨自己的下一跳。直觉上，拨通花的时间就该是这一段的延迟——
**但内核态转发下并不是。**

nftables 的 DNAT 发生在 `PREROUTING`：包还没进下一跳的协议栈，目标地址就被改写、
直接转发走了。下一跳**自己从不接这个连接**，SYN-ACK 是从更下游回来的。
于是拨转发端口量到的，是「本机 → 下一跳 → …… → 落地」的整条往返。

实测（腾讯云 → 香港 → 落地，两跳都是内核态）：

| 落地目标 | 第 1 跳拨通耗时 | 第 2 跳拨通耗时 | 差值 |
|---|---|---|---|
| 马来西亚 | 37 ms | 31 ms | 6 ms |
| 台湾 | 25 ms | 19 ms | 6 ms |
| 香港本地 | 8 ms | 9 ms | ~0 |

第 1 跳明明是同一台机器、同一条网络路径，数字却跟着**落地目标**变——
因为它量的从来就不是这一段。真实的腾讯云→香港只有 6 ms 左右。

所以面板分开报两个数：

| | 怎么来的 | 拿来干嘛 |
|---|---|---|
| **本段延迟** | 单独拨下一跳机器的**探测端口**（默认 SSH 22），那个端口会在它本地终结 | 判断**哪一段慢** |
| **拨通耗时** | 拨下一跳的转发端口 | 判断**通不通** |

探测端口开着关着都行：关着的话对方内核回 RST，往返时间一样准。
唯一量不到的情况是那个端口被防火墙静默丢弃，这时候页面会说明原因而不是显示 0。

> 用户态转发不受这个影响——它的 relay 在本地接下连接再另建一条到上游，
> 两个数字本来就一致。但为了口径统一，两种模式都照样单独量。

## 部署建议

面板保存着各节点的 SSH 凭据，是高价值目标。**不建议直接暴露在公网。**

推荐只监听 `127.0.0.1`，前面用 Nginx 反代 + HTTPS：

```nginx
server {
    listen 443 ssl http2;
    server_name panel.example.com;

    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;

        # 探针走 WebSocket 长连接，这两行必须有
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 长连接不能被反代掐断
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

反代后面记得开启 `trust_proxy_headers: true`（或环境变量 `PANEL_TRUST_PROXY=true`），
否则日志里记录的是反代的 IP。

**需要备份的文件**（都在数据目录下）：

- `panel.db` —— 流量账本与全部配置
- `master.key` —— 凭据解密密钥。**丢失后所有 SSH 密码和 DNS 凭据都无法解开，只能重新填写**

## 配置

启动期配置见 [`config.example.yaml`](config.example.yaml)。
运行期参数（离线判定阈值、失败次数、切换冷却、通知渠道、数据保留天数）
在面板的「设置」页面里修改，无需重启。

几个值得说明的参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| 离线判定阈值 | 90 秒 | 心跳超过这个时长没来即认为探针失联。探针默认 30 秒上报一次，留了三倍余量 |
| 连续失败次数 | 3 | 达到这个次数才真正判定下线，避免一次网络抖动就把域名切走 |
| TCP 拨测 | 开启 | 探针失联后再拨一次端口确认。探针进程崩了但机器仍在跑业务时不应切换 |
| 切换冷却 | 300 秒 | 两次自动切换的最小间隔，防止状态在临界点抖动导致解析来回改。手动切换不受此限制 |
| 计费倍率 | 1.0 | 网卡层统计与商家计量口径通常差几个百分点，用它校准 |

> 配额建议设为商家标称值的 95% 左右，留一点余量。

## 测试与验证

```bash
make test       # 单元测试
make test-race  # 带竞态检测
make e2e        # 端到端：起真实面板 + 探针，34 项断言
```

端到端脚本覆盖的场景：

**流量账本**

1. 探针上报 → 面板账本累加
2. **机器重启（`boot_id` 变化）→ 账本继续累加而不是归零**
3. 面板进程重启 → 账本不丢
4. 重复上报同一份报文 → 不重复计账
5. 单向计费口径确实按较大方向计算

**配额与处置**

6. 流量到达预警线 → 产生预警事件
7. 流量耗尽 → 状态转超额、写入事件、不误触发关机
8. 探针后续心跳不会把超额状态刷回在线
9. 手动清零 → 用量归零、上周期归档、超额限制解除

**端口转发**

10. 多跳规则的入口地址与逐跳目标推导正确
11. **转发计数只进转发账本，节点账本一个字节都不多**
12. 实际消耗流量的换算结果与节点用量对得上
13. 转发计数重复上报不重复计账、`epoch` 变化按归零处理
14. 上报里带已删除的跳时不会让整次上报失败
15. 监听端口留空时确实从配置的端口范围内分配
16. **多入口共用同一个监听端口，且两个入口都被列为可连地址**
17. 中间跳配多个节点会被拒绝（链路中段不允许分叉）
18. 链路测试逐段返回结果，并带回节点侧的转发能力自检
19. 节点被禁用时规则明确报告未生效原因

另外：DNS 三家服务商的签名与请求构造有对应的单元测试（`httptest` mock）；
选主逻辑（优先级、超额淘汰、冷却期、全员不健康时保持现状）有独立测试。

转发数据面的单元测试**全部不需要 root**：nftables 规则渲染与计数解析是纯字符串/JSON 处理，
内核后端在测试中替换为假实现，用户态 relay 与预连接池则起真实的本地监听来测
（包含「连接池探活不能吃掉上游先发来的首字节」这条）。
真正需要 root 的只有把规则落到内核这一步。

> 首次配置真实域名时，建议先用面板上的「切换演练」确认选主结论符合预期，再交给自动切换。

## 已知限制

**流量统计**

- 流量口径与商家不完全一致。`/proc/net/dev` 统计的是网卡层字节，商家可能按 IP 层计算，
  是否含协议开销也各家不同，通常差几个百分点。用计费倍率校准。
- 容器里跑探针时，`/proc/sys/kernel/random/boot_id` 取到的是宿主机的，多个容器会撞成同一个值。
  用 `VPS_AGENT_BOOT_ID` 给每个容器指定不同的值。

**处置动作**

- 面板只能关机，不能开机。没有带外管理权限，被关掉的机器需要到服务商后台手动开启。
  新周期开始时面板会解除超额限制，但机器仍需自行启动。

**端口转发**

- 限速只作用于出方向，这是 tc 的固有限制。对中转机影响不大：
  转发的两个方向都是本机出方向，因此一条规则的上下行会共享同一份带宽。
- 需要探针以 root 运行，且机器上有 `nftables` 与 `iproute2`。
- **云服务商的安全组 / 防火墙管不了**。转发用的入口端口仍需自行到服务商控制台放行，
  那一层在机器外面。链路测试说每一段都通、客户端却连不上，基本就是这个原因。
  （链路测试只测机器与机器之间那几段，不含「客户端 → 入口」——
  面板常常只监听内网，和客户端走的不是同一条网络路径，拿它拨一次说明不了问题。）
- 修改转发规则会重置该规则的流量统计。跳是整组重写的，跳的 ID 变化，分账随之从头开始——
  改了跳序之后，旧的用量本来也对不上新拓扑。只切换「启用 / 停用」不会重置。

**其他**

- 单管理员账号，没有多用户与角色权限。

**阿里云 CDT**

- CDT 用量取的是阿里云自己算的「本月至今累计值」，不是面板算的。它有几分钟延迟，
  所以熔断也会跟着晚几分钟——想留余量就把熔断线调低一点。
- 免费额度的规则是阿里云定的，会变。面板把两个池的额度做成可配置的，
  规则变了在界面上改数字即可，不用等更新。
- 定时开关机判定的是「此刻的 HH:MM 是否等于设定值」，面板停机超过一分钟会错过那个点，
  **不会补执行**——补一个半小时前的关机指令比错过它更让人意外。

**探针远程升级**

- 依赖 systemd 的 `Restart=always` 把退出后的探针拉起来。一键安装脚本装出来的服务就是这样配的；
  手工用别的方式跑探针（比如直接 nohup）的话，升级完它就不会自己回来了。
- 面板上得有对应架构的探针二进制。缺哪个架构，节点列表上方会直接提示。
- 面板认为的「最新版」是编译进它自己的版本号。面板和探针二进制是分别下载的，
  理论上可能不同版——所以升级完以节点实际报回来的版本号为准。
